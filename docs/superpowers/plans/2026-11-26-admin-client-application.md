> **For agentic workers:** After user review, use `superpowers:executing-plans` inline, one approved increment at a time. No routine delegation. Checkboxes record implementation, not planning completion.

**Goal:** Build the accepted local application with admin-first fresh setup, configurable independent capacity, live lifecycle controls, concurrent meetings, real create/join, shared client sessions, logs/console and the accepted client UI.

**Architecture:** Keep Chord, Raft, PostgreSQL, runtime authority and the existing participant protocol/session. Separate supervised backend capacity from explicit meeting/client operations. **Tech stack:** Existing Node/TypeScript, Go/Raft, PostgreSQL, SQLite, HTTP/WebSocket, browser HTML/CSS/JS and Docker/mediasoup. No new framework or dependency is proposed.

## Global constraints

- Independent Discovery Peers / Consensus Nodes / Meeting Servers / Media Servers; minimum **1**, defaults **4 / 3 / 2 / 1**. Keep discovery and consensus separate. Accept even voter counts.
- Final entry opens administration without creating meetings or participant sessions. Presets configure capacity; any demo population is a separate explicit operation after backend startup.
- Role hints are limited to **Owner** and **Leader**; ownership is per meeting, not a lab-wide exclusive role.
- Preserve quorum/barrier reads, matching Raft READY and SQL ACTIVE ownership, generations/incarnations, SQL/runtime/SFU fencing, local capture ownership, explicit browser capture, FIFO sharing, private-group authorization and original-command uncertainty. Keep one participant protocol.
- Reuse bounded external commands, exclusive supervisor locks, exact child handles, owned container/volume identity and journal verification. Missing state requires restoration; uncertain ownership never permits PID killing, lock deletion, automatic rebootstrap or destructive reset.
- Defer network editing, arbitrary link/UDP faults, latency, pause/global time, full shell/PTY, zero-start, general autoscaling/replacement management, installers and deployment. Explicit Create Meeting/Add Node provisioning remains required.
- Preserve unrelated work, especially `package-lock.json` and accepted design artifacts. No installs or lockfile regeneration are needed. Commit only coherent verified implementation increments after authorization; no push/merge/deploy.

## Fresh-run scope and proposed engineering choices

Fresh-only startup follows the user's scope reduction. The capacity bounds and media design below remain engineering recommendations for review.

**Fresh backend on every Start.** Allocate a new run/cluster, Raft directories, SQL Compose project/volume and journal namespace. Do not load previous configuration, meetings or clients. A supervisor-level lock must be checked before allocating another run: a new UUID is never a way around uncertain old ownership. Keep run resource records for exact owned shutdown and diagnosis; ordinary shutdown need not delete old files/volumes. Leave existing demo data untouched, with no import, archive browser or automatic cleanup project. Permanent deletion remains a separate explicit action. Repeated runs can leave retained artifacts; none are advertised as resumable backends.

**Keep durability within a running backend.** PostgreSQL/Raft state, session journals, operation IDs and retirement records still protect node/client crashes, retries, browser reload and original-command uncertainty. A restarted node reuses its current-run identity with a new incarnation; restarting a client uses that run's same journal. Recover incomplete operations while the supervisor remains alive. Whole-supervisor death retains the existing ownership/manual-cleanup blocker; there is no new automatic restoration feature. Removing Resume does not authorize discarding state during failover or silently recreating missing initialized stores.

**Initial supported bounds: 1–5 of each backend role, independently.** These are proposed local-lab limits, not protocol limits or fixed presets. Validate them in API and UI and test the endpoints; widening them is later bounded work. This includes 1, 2 and 5 without changing the existing nine-helper routing bound. Quorum is `floor(voters / 2) + 1`: 1/2/5 voters require 1/2/3; one or two voters cannot lose one and keep progress. Only show the 4+ discovery assignment hint below four. Keep existing eight-media-peer room limits; propose at most 16 retained meeting records and 32 client records per backend for bounded inventory. Explain exhausted capacity rather than spawning indefinitely.

**Media: one real media node/container with isolated rooms per meeting.** A node starts with an empty room registry, a worker/listener and a supervisor-only management capability. Provision a distinct router, `KernelFence`, owner/grant state, peer map and room capability for each explicitly allocated meeting; share only the worker/listener. One media node can then serve two concurrent meetings, independently of the meeting-server count. No browser can create a room or supply an SFU route. The current kernel does not provide this isolation: implement and prove it in increments 2 and 5.

Alternatives considered: one current kernel/container per meeting preserves isolation but makes the Media Servers count a count of slots, or introduces a second host-controller hierarchy; neither fits the accepted independent capacity well. Restarting every runtime whenever a room is created interrupts unrelated meetings and still does not solve the single-room kernel. An immediate dashboard reskin leaves these lifecycle gaps intact. Recommend staged supervisor extraction plus explicit media rooms. The larger costs are durable membership/drain and media isolation; the layout work is smaller.
