Draft 6 · Design & Scope Notes

Standalone visual proposal with illustrative data. Add, remove, console and client actions change sample state only. No application services are contacted, no real processes or messages are affected, and no private URLs or backend data are loaded.

Latest Layout

One sidebar contains meetings, discovery peers, consensus nodes, meeting servers, media servers, storage and clients. The middle has details appropriate to the selected item, with logs below it. A selected client shows session and meeting controls; a selected meeting shows its owner and participants. The source dropdown can broaden the logs beyond the selected item. Detail tabs contain only Overview and Actions. Logs remain in the independent bottom viewer, with sidebar selection and its source dropdown controlling what is shown.

Multiple Meetings And Owner

Multiple concurrent meetings are an explicit requirement. Owner means a meeting server owns one or more meetings, not exclusive ownership of the whole lab. The detail table lists each meeting and its generation, and selecting a meeting shows that meeting's owner. The preview has two meetings assigned to one server to demonstrate this. Coordination metadata, SQL storage and RuntimeAgent already distinguish meetings and can track multiple assignments; the launcher currently creates and recovers one meeting, and each current SFU kernel is bound to one meeting. General multi-meeting creation, recovery orchestration and per-meeting media provisioning remain implementation work. Arbitrary SFU sharing or seamless failover is not claimed.

Add, Leave And Crash

Contextual plus buttons add a role in the preview. Minus controls appear on row hover, keyboard focus, and touch devices, with accessible names and tooltips. Removing a backend node means graceful role-specific departure: Raft removal requires healthy quorum and cannot remove the last voter; meeting servers must drain/handoff before stopping; discovery exits and route repair differ from voter membership. The preview includes only illustrative guards and handoff, not protocol execution. Stopping a client process retains its journal and membership, while durable Leave Meeting is a separate confirmed action. A crash never implies voter removal or durable participant leave.

Actions And Scope

Crash, Restart and graceful Leave remain in backend Actions. Client Actions include process management, browser access, meeting messaging and distinct Leave Meeting. Meeting Actions include owner inspection and Close Meeting. Network editing is omitted for now: existing TCP cut/heal fixtures are not a general admin fault service, and configurable delay needs traffic/proxy wiring. TCP controls would not simulate UDP/RTP media loss. The user permits dropping network editing unless relatively easy; no such low-cost operational path has been established. Pause/resume also remains deferred. Initial counts are independent and minimum 1; live addition and graceful removal are intended capabilities. Automatic target-capacity/replacement management and a full OS shell remain deferred. The command console proposes a restricted operation interface using the same action handlers.

Fresh Backend Setup

Resume has been dropped as a convenience feature. Backend Setup has presets above capacity and a Start button. Every launch creates an empty backend in a new namespace; old runs are not reopened or imported. Existing files are left alone, with no archive manager. Node/client restart, browser reattachment and meeting failover within the running backend still retain their state and safety checks. Fulfilled P2P hints are hidden. Remaining hints each occupy a separate line. Bottom copy states that users can add/remove later.

Implementation Boundaries

Existing Chord join/routing and low-level Raft admission/promotion/removal can be reused. Configurable inventory, persistent identities and counts, live process lifecycle, guarded retirement, route/discovery refresh, general meeting/client creation, multi-meeting media provisioning and authenticated dashboard log/command transport still need work. Existing helper-route lists cap at nine endpoints. One or two voters cannot maintain quorum after one failure; a P2P demonstration needs at least four discovery peers. Preserve shared journals, original command uncertainty, invite-only group history, one participant protocol, SQL/consensus fences, capture ownership and browser permission. These mockup revisions do not authorize app implementation.
